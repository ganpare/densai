セキュリティ警告（最優先）

GitGuardian：ハードコードされたシークレット検出 → これが唯一の「失敗」チェック。PR内のどこかに秘密情報（トークン／鍵／パスワード）が残っています。即削除・無効化・ローテーションが必要。

SESSION_SECRET の既定値が弱い（docker-compose.yml）。未設定でも動いてしまうため、必須化推奨（${SESSION_SECRET:?…}）。

PDFダウンロード経路のパストラバーサル（server/routes.ts）：pdfFilePath をそのまま信用してダウンロードできてしまう経路があり、任意ファイル読み取りのクリティカルな脆弱性。
→ DBにはファイル名のみ保存し、ダウンロード時はサーバ側で uploads/pdfs を基点に path.join 再解決する方式へ。

Docker/起動モードの不整合

Dockerfile/Compose が「dev用」コマンドで本番起動（npm run dev）。一方で Dockerfile は --only=production で依存を絞っていて dev依存が欠落。
→ 本番は npm ci（or npm ci --omit=dev + npm run start）に合わせて CMD ["npm","start"] へ。
→ Composeの command: npm run dev と 開発用のボリュームマウント（.:/app, /app/node_modules） は override（dev用）に移動。

DB初期化のレース＆本番不適合

initializeDatabase() を await せずモジュールロード時に実行 → 初期化前にDBを使い始めるレース。

さらに child_process.exec('npm run db:push') を本番コンテナで実行しており、環境次第で失敗しやすい。
→ サーバの起動前に明示的に await、DBマイグレーションは エントリポイントやComposeの command / 専用ジョブで実行（例：node ./scripts/migrate.js && node dist/server.js）。

ファイル名サニタイズが強すぎる

sanitizeFilename が多くの文字を _ に置換 → 識別子が潰れる可能性。
→ 許可リストを広げる（英数・-_.() など）／長さ制限＆二重拡張子対策で実運用バランスを取る。

コンフリクトの性質

DB層（Postgres化）＋ ルーター（PDF系エンドポイント）＋ クライアントのPDFフローで大きく変えており、直近の修正と差分が衝突。

package-lock.json も競合 → 片側に寄せるとビルドが壊れやすいので、いったん lockfile を捨てて npm ci で再生成が安全なことが多い（Monorepo構成や厳密固定が必要なら慎重に）。

具体的な対処順（これで「赤→緑」に持っていく）

シークレットの除去＆ローテーション（最優先）

PR内の秘密を即削除し、履歴にも残っていたら git filter-repo 等で履歴からも削除。

影響する外部サービスのキーは無効化して再発行。

.env.example にダミー値（例：CHANGE_ME）を置く。

docker-compose.yml の SESSION_SECRET は 必須化：

SESSION_SECRET: ${SESSION_SECRET:?SESSION_SECRET must be set in .env}


PDFパスの固定化（パストラバーサル封じ）

DBにはファイル名（basename）のみ保存。

参照時は const full = path.join(UPLOADS_PDFS_DIR, basename); で再構成し、fs.stat で存在確認後に res.download(full, basename)。

生成APIのレスポンスも 公開パスではなくサーバ側で解決したフルパス＋ファイル名を返す。

これは CodeRabbit が示した差分案をほぼそのまま適用すればOK。

Docker本番化

Dockerfile

RUN npm ci（dev依存が不要なら --omit=dev と npm run build→npm start の組み合わせ）

RUN npm run build

CMD ["npm","start"]

docker-compose.yml（本番）

command: npm run start

ボリュームは PDF保存用（./uploads:/app/uploads）のみ残し、ソースのバインドは削除。

docker-compose.override.yml（開発）

command: npm run dev

.:/app, /app/node_modules をここに移動。

DB初期化のレース解消

サーバ起動前に必ずマイグレーション。

例：ENTRYPOINT ["sh","-c","npm run db:migrate && node dist/server.js"]

もしくは main() の中で await initializeDatabase() を呼び、完了後に app.listen(...)。

npm run db:push を child_process で投げる設計は回避。

ファイル名サニタイズの見直し

例：

// 例：英数・空白・.-_() を許容、連続ドットと先頭ドットは弾く、長さ制限
function sanitizeFilename(name: string): string {
  const base = name.replace(/[^a-zA-Z0-9 ._\-()]/g, '');
  const noLeadingDot = base.replace(/^\.+/, '');
  const singleDots = noLeadingDot.replace(/\.+/g, '.');
  const trimmed = singleDots.trim();
  return trimmed.slice(0, 120) || 'file';
}


さらに 実際の保存時は一意なプレフィックス（reportId や UUID）を先頭に付与して衝突回避。

コンフリクト解消の方針

server/routes.ts：上記PDFパス修正を基準に取り込む。

server/db.ts：await化・本番でのマイグレーション戦略を優先（child_process依存を排除）。

server/storage.ts：pdfFilePath → pdfFilename 運用に合わせた型・保存処理に統一。

client/...report-detail-modal.tsx：2段階（生成→ダウンロード）フローで返却値の filename / pdfPath 仕様に合わせる。

package-lock.json：ビルドが通らない場合は いったん再生成（rm package-lock.json && npm ci）を検討。
